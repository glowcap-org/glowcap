# Design: every bench reports on the performance page

## Goal

Every `bench-*` build command contributes a report — a chart where one is
natural, a value table otherwise — to the public performance page
(`site/content/performance.smd`). The reports are regenerated by **one command**
so they cannot drift from the harnesses, and they carry the same dated,
one-machine, "measure your own" framing the Goblins section already uses. No
leaderboard language.

This closes the gap noted earlier: the current Goblins charts are hand-built
inline SVG produced by a throwaway script, with no repeatable path.

## Scope

Four benches, four reports:

| bench command        | report on the page                                            | chart?                                       |
| -------------------- | ------------------------------------------------------------- | -------------------------------------------- |
| `bench-codec`        | Syrup vs Cap'n Proto encode/decode MB/s, ns/op                | grouped bars + table                         |
| `bench-peer-scaling` | bytes/connection per scenario, 500k extrapolation             | bars + table                                 |
| `bench-goblins`      | latency p50 + throughput per suite (already present)          | grouped bars + table                         |
| `bench-frame-view`   | alloc budget (`per_turn`), struct sizes, iteration throughput | table only (it is an assertion, not a curve) |

Out of scope: gating any wall-clock number; a stale-check on the generated
regions (bench numbers legitimately vary by machine, so "did you regenerate" is
not a meaningful gate — unlike `gen-header`).

## Architecture

### Component: `bench/site_report.rkt` (the generator)

One Racket program that owns the whole refresh. Racket because the Goblins bench
and `bench/goblins/report.rkt`'s SVG-bar renderer are already Racket; reusing
them keeps a single charting implementation rather than the three (Racket Zig,
Python) we would otherwise accumulate.

Responsibilities, in order:

1. **Run each bench in ReleaseFast and capture stdout.** Shell out to
   `zig build bench-codec -Doptimize=ReleaseFast`, `…-frame-view`,
   `…-peer-scaling`, and `zig build bench-goblins`. The first three are Zig
   benches that print structured lines; the Goblins step is the existing Racket
   bench. This is minutes of compile plus a ~70s Goblins run, which is why it is
   a manual refresh tool and **not** part of `zig build check`.
2. **Parse** each bench's stdout into a small record (see Data below).
3. **Render** per bench: a compact grouped-bar SVG (codec, peer-scaling,
   goblins) and/or an HTML value table (all four), themed to the site palette
   (Goblins teal `#257f88`, pancake amber `#c76f18`, ink `#3a3027`).
4. **Splice** each rendered region into `performance.smd` between markers, and
   regenerate the machine/date stamp. Surrounding prose is left untouched.

### Shared rendering

`bench/goblins/report.rkt` already renders grouped-bar SVGs. Factor its bar
geometry so both the suite's full-size SVG (760×430, title + legend) and the
site's compact variant (≈380×210, no title/legend — the page supplies a caption
and swatch legend) share one code path. The compact renderer is the one the
generator uses.

### Splice markers

Each bench's generated content is **one `=html` fenced block**, because Zine's
`=html` fence writes raw HTML verbatim (verified: `render/html.zig`
short-circuits `=html` and skips language validation), so a bare
`` ```mermaid `` would fail the build but raw `<svg>`/`<table>` does not. The
block begins with a marker comment:

````
```=html
<!-- bench:codec | generated by `zig build bench-site-report`; edits are overwritten -->
<div class="bench-legend">…</div>
<div class="bench-charts">…<svg>…</svg></div>
<table>…</table>
````

```
The generator locates each `=html` block by its `<!-- bench:<name> | … -->`
marker (the comment is raw HTML, invisible in the page) and replaces from the
opening fence to its closing fence. The page-wide stamp lives in its own
`<!-- bench:stamp | … -->` block. Markers double as "do not hand-edit" notices.

### `performance.smd` restructure

Under "What the benchmarks report", each bench gets:

- a `## heading`,
- one or two sentences of hand-authored prose ending in a "measure your own"
  invitation with the bench's own build command,
- its generated `=html` region.

The existing Goblins section converts to this shape; its hand-built inline SVGs
are replaced by generated ones. A single generated stamp line (`<!-- bench:stamp -->`)
near the top of the reports states the machine and date for all four.

### Build wiring

A new sibling build step `zig build bench-site-report` (needs `racket` +
`goblins`) runs the generator. Documented in `.agents/rules/cli.md` and
`bench/goblins/README.md`. Not part of `check`.

## Data

Parsed records (all numbers `f64`/int from the stdout lines the benches already
print):

- **codec**: per `(op ∈ {encode, decode}) × (codec ∈ {syrup, capnp})`:
  `ns_per_op`, `mb_per_sec`; plus `dispatch turns_per_sec`. Source lines:
  `encode codec=syrup … ns_per_op=… mb_per_sec=…`, `dispatch … turns_per_sec=…`.
  Chart: grouped bars, x-axis `[encode MB/s, decode MB/s]`, series syrup/capnp.
- **peer-scaling**: per `scenario ∈ {idle, warmed, active16}`: `bytes_per_conn`,
  `mem_at_500k_gib`. Source: `peer_scaling scenario=… bytes_per_conn=… mem_at_500k_gib=…`.
  Chart: single-series bars of `bytes_per_conn`; table adds the 500k GiB column.
- **goblins**: per suite: `p50`, `rps` (and p99/p999 for the table). Source:
  parse the Goblins bench stdout (`  goblins  p50=…ms … rps=…`) — already
  structured per suite/backend.
- **frame-view**: `wire_path per_turn`, `model_layout` struct sizes,
  `frame_view iterations/bytes`. Table only.

## Honesty model

Each region is a dated, ReleaseFast, single-machine snapshot. The generated
stamp names the machine (uname/nproc/meminfo) and toolchain versions
(`racket`, `zig`, `goblins`). Per-bench prose ends with the reproduce command.
No "N times faster", no "scoreboard", no "leaderboard" framing — the data plus
the command carry it.

## Testing

- **Parser unit tests** (`bench/site_report-test.rkt`): feed captured sample
  stdout for each bench, assert the parsed records. These are the load-bearing
  correctness check and need no toolchain to run.
- **Render shape checks**: assert each renderer emits well-formed `<svg>`/`<table>`
  with the expected number of bars/rows for sample data.
- **`zig build site`** must pass after a regeneration — it validates the spliced
  `.smd` parses and the `=html` blocks are well-formed.
- **`zig build meta-check`** for the new documented build step.

## Risks / tradeoffs

- **Refresh cost**: ReleaseFast compiles + a Goblins run make the tool minutes
  long. Acceptable for a manual, on-purpose refresh; explicitly not in `check`.
- **Goblins libpancake optimize mode**: the Goblins bench builds `libpancake`
  via the Racket binding; the plan must confirm whether `-Doptimize=ReleaseFast`
  reaches it, and the stamp should record the mode actually used.
- **Generated content in a committed source file**: mitigated by clear markers
  and the `gen-header` precedent (pancake already generates into committed
  `include/pancake.h`).
- **`=html` HTML tables** instead of Markdown tables for the generated regions:
  slightly more verbose, but keeps one fully-controlled block per bench and
  avoids Markdown/`=html` boundary edge cases.
