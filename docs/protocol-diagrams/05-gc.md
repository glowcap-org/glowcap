# Garbage collection

Anchors: CapTP Specification § op:gc-exports, § op:gc-answers. Wire labels per
the spec and Goblins (`op:gc-exports` carries parallel position and delta lists;
`op:gc-answers` carries positions only).

## GC-1: Export refcount lifecycle

An export row's wire count goes up each time the position crosses the wire and
down by gc deltas. The row releases only at zero. Export positions are monotonic
within a session and are never reused.

```mermaid
stateDiagram-v2
    [*] --> Live: first export, wire count 1
    Live --> Live: re-export increments wire count
    Live --> Live: gc-exports delta decrements, count above zero
    Live --> Released: gc-exports delta brings count to zero
    Released --> [*]: row released, position retired
```

## GC-2: op:gc-exports with wire-deltas

The importer tells the exporter how many wire references it is dropping per
position. The message carries two parallel lists: positions and deltas.

```mermaid
sequenceDiagram
    participant I as Importer
    participant E as Exporter
    E->>I: op:deliver (payload exports position 3)
    E->>I: op:deliver (payload re-exports position 3)
    Note over I: import row 3 has wire count 2
    Note over I: local refs to import 3 all dropped
    I->>E: op:gc-exports (positions [3], deltas [2])
    Note over E: export 3 count minus 2 reaches zero, row released
```

## GC-3: Why deltas: the resurrection race

A bare "release position 3" would race a re-export of 3 already in flight.
Counting deltas makes the race benign: both sides converge on the same nonzero
count and the export stays live.

```mermaid
sequenceDiagram
    participant I as Importer
    participant E as Exporter
    par gc crosses a re-export in flight
        I->>E: op:gc-exports (positions [3], deltas [1])
    and
        E->>I: op:deliver (payload re-exports position 3)
    end
    Note over E: count 2 minus 1 = 1, export 3 stays live
    Note over I: import row 3 revived at wire count 1
```

## GC-4: op:gc-answers

The questioner releases answer positions it allocated. Answer positions are
single-reference, so there are no deltas: a listed position is released
outright, and the answerer drops the row along with any resolver bookkeeping
tied to it.

```mermaid
sequenceDiagram
    participant Q as Questioner
    participant R as Answerer
    Q->>R: op:deliver (..., answer-pos 11)
    Q->>R: op:deliver (..., answer-pos 13)
    Note over Q: results no longer wanted
    Q->>R: op:gc-answers (positions [11, 13])
    Note over R: answers-owed rows 11 and 13 dropped
```
