# Changelog

Every release lists what changed for people using glowcap, in the form
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) describes. The
release notes on each [GitHub release](https://github.com/glowcap-org/glowcap/releases)
open with that version's section, so a release needs its section here first.
glowcap is alpha software, and a minor or patch version can change APIs, ABIs,
and storage formats before 1.0.
Releases before 0.1.7 are in the
[earlier changelog](docs/history/CHANGELOG.md).

## [Unreleased]

### Added

- Every Rooms session activity event now carries `mentions`, which says whether the line names you or the whole room. The session decides it once from the line's Markdown, so every reader agrees.
- A program can attach to a running Rooms session over CapTP with a session link, using the `rooms_services::session::attached` Rust library. It reads activity after a saved position, posts lines that stay editable and withdrawable, shows typing, and moves file bytes. With the session's management link it also issues, lists, pauses, resumes, and revokes access.
- `glowcap apps rooms session access issue` prints a link to your running session for an observer, collaborator, or administrator. Use the id from `list` to pause, resume, revoke, or forget an access. A revoked access keeps one entry under its original id, and `forget` refuses an access that still works. An interrupted issue reserves its id until you retry with the original label and rights or forget it. If another issuer has taken its place or its receipt has expired, forget the unfinished id and issue again.
- `glowcap apps rooms session access share-management --id` prints a management link for one access. A browser adds it under **Session access** to pause, resume, or revoke that access.
- `glowcap apps rooms bot` keeps a coding agent (Claude, Codex, or Pi) present in Rooms through a session link. `serve` runs it and shows it typing while its agent works, and `status` reports it. A line that is exactly `/reset` starts a new agent conversation, and `--instructions` adds your own instructions to every reply, which `--no-instructions` drops.
- During a turn the Rooms bot's agent calls `say`, `send`, and `command` a fixed number of times at most, and `workspace`. `say` and `send` post in the turn's conversation or in another with `--conversation`. With `--dm` they post privately, opening a direct message with a member of the turn's directory or reusing the open one.
- The Rooms bot has exactly the rights of its access, so narrower rights limit what it does. The rooms and directory you place it in decide who can reach it, and `--conversation-limit` bounds how much one conversation can start in an hour. A bot answers only while its access is active, and a full bot belongs in a container or under its own user, as the [bot guide](docs/rooms/bot.md) says.
- A turn the Rooms bot's agent could not answer shows in `bot status` as `unanswered` with its kind and the next step. `bot ready` fails after a refused agent sign-in until a later turn is answered or the bot restarts. A revoked access ends the bot with a failure that names `serve --link - --replace-link`. A first start whose link the session refuses stores no settings and no link. A replacement link is stored once the session has answered it, and `serve` exits with a failure that says so when the session refuses it.
- A Rooms bot has a home, `home/` in the bot directory, that its agent keeps across every conversation and restart. `/reset` and a new link leave it alone. The agent saves one small file per memory in `home/memory/` and sees their list, newest first, before every reply. `bot status` reports the home and how many memories it holds, and a deployment keeps the home in its own volume, `glowcap-rooms-bot-home`, so starting the bot fresh keeps it.
- A Rooms deployment can run a bot as Compose services in your override, and [Run a bot](apps/rooms/web/deploy/README.md#run-a-bot) has the steps. `glowcap apps rooms bot ready` is a container health check. It exits 0 only while a `serve` holds the bot directory, its access is active, its session answers, and its agent is not refused its sign-in. Each `bot serve` setting except `--replace-link` and `--no-instructions` is also the variable `GLOWCAP_ROOMS_BOT_<NAME>`. `up` also names the selected image `glowcap-rooms:selected`. You copy `bot.Dockerfile.example` from an installation's `share/glowcap/deployment/` to `bot-image/Dockerfile`, and it takes the agent as the build arguments `AGENT_PACKAGE` and `AGENT_DIR`.
- A bot directory with an unreadable state file is refused, and Compose then restarts the bot again and again. To start it fresh, follow [Give the bot a new link](apps/rooms/web/deploy/README.md#give-the-bot-a-new-link).
- `bot serve` refuses a stored `config.json` that holds a field it does not read, and a `GLOWCAP_ROOMS_BOT_` variable it does not read, and names each one. A fresh start of a bot directory with an unreadable state file drops its settings, link, and place in the session. The bot then answers only lines sent after it starts.
- After `--replace-link`, the bot never sends a reply line twice that the old link was sending. A replacement link to the same access, or back to a link that was never revoked, settles what that access sent, and `bot status` counts the lines another link finished as `replaced_lines`. A reply line whose receipt the session would not take back shows as `unreleased_lines`. A reply line or `--dm` open that stalled, because the session stopped waiting for its result, is given back, and the session ends it. A `--dm` open given back is never sent again.
- A `--dm` open the session has not settled stays in `opens/` as a note and counts toward the `--dm` limit. To clear it, give the bot a new link with `--replace-link` and then revoke the old access. A note another access sent shows in `bot status` as `replaced_opens`. A first start refuses a bot directory whose `opens/` holds notes, with the same way out as a missing `config.json`. The session gives back a revoked access's receipts once they can no longer change, including an open sent before a session restart, so their places are free again.
- The Rooms bot starts a fresh session when Pi no longer has the stored one, as it does for the other harnesses, instead of answering every turn of the conversation with a declined failure. A pause or halt gives the run after it a whole deadline even when its cut-off could not be saved, and a give-up whose reply save a halt interrupted is recorded once the reply lands. The serving loop waits at most 100 ms for a note count held by a verb and asks again on its backoff.
- A session `release` of a result whose executor is still running now fails with class `busy` and retry `soon`, not `uncertain`: release again.
- A Rooms bot rerun of a turn whose run did not answer is told what each of that run's `say`, `send`, and `command` actions did, from the bot's own claims, and says the session's history shows more only when the run resumes a stored session. The claims live in `turn-actions/` and hold the action and its outcome. A bot directory's old `actions-held/` is unused and may be deleted.
- The Rooms bot keeps or gives back the receipt of every `say`, `send`, and `command` its agent runs. An action still running when its verb returns prints `"settling": "bot"`, and the bot settles it after the turn, across restarts too. The bot finds such actions in the session's list of the receipts its access holds, so it also settles a request that reaches the session after its verb died. An action whose receipt the session would not take back shows in `bot status` as `unsettled_actions`, and one the old access still held after `--replace-link` as `replaced_actions`. A replacement whose old access cannot list its actions exits without storing the new link, unless that access is paused, which `replaced_unlisted` then says. The bot refuses a new action while as many are claimed in `turn-actions/` as the session keeps receipts.

### Changed

- The Rust binding's `Attachment::start_live` is now async. It resolves with the confirmed `LiveIncarnation`, or the startup's exact failure, and settles with the closed error if its Host closes, where it used to return at once and leave you to poll `live_marker`. Await it, then use the incarnation or its new `marker()`. `live_marker` and `live_incarnation` stay as reads.
- A Rooms upload never pauses once its post is acknowledged. It fills its files a piece of each in turn, and a round of one piece of each file that does not finish within 14 seconds ends it with the line posted, its files marked incomplete, and the cause, the room's own words when the room refused a write. A fill that outlasts the session's 120 second running bound now completes while each round keeps its own, and the room restarts a file's lease at the post. The Rooms bot's `send` waits for that outcome within its verb's budget and prints `files` as `complete`, `incomplete` with a `reason`, or `unfinished` when its wait ended first. The files stop with the verb. `bot status` shows in `last_error` an action's line the bot could not keep yet.
- A Rooms session that saved receipts under [0.1.8](#018---2026-11-20) no longer opens, and nearly every session that ever sent a message saved some. `session start`, `session serve`, and the page say so when they refuse it. Start a new session wherever one was saved:
  - A session you run from a terminal: keep its directory as it is and run `glowcap apps rooms session start` with a new `--dir`. A bot that speaks as that session needs a new bot directory too, so serve it with a new `--dir` and an access from the new session. Move its `home/` across first to keep what its agent saved.
  - A session kept in your browser: **Delete browser data…** under **Advanced** on the session setup page starts a new one and erases the old one.
  - A Compose deployment's shared session, in the `glowcap-rooms-session-state` volume: back it up and run `glowcap apps rooms deployment reset session`, which prints new use and management links. Every member attaches again with the new use link, and every access the old session issued needs a new one.
  - A Compose deployment's bot: remove its session volume, `glowcap-rooms-bot-session-state`, and its state volume, `glowcap-rooms-bot-state`, keep its home volume, and set the bot up again. It answers only lines sent after it starts.

  [A session the new version cannot read](apps/rooms/web/deploy/README.md#a-session-the-new-version-cannot-read) gives a deployment's steps in order.
- A Rooms session whose every receipt place holds an unfinished request refuses a new request before it runs, with the class `receipts-full`. The Rooms bot keeps a reply refused this way and posts it once a place is free. `bot status` shows the refusal in `last_error`.
- A Rooms session keeps a receipt its access gave back, settled as released, until newer receipts push it out. A request sent again while its receipt is kept is answered from that receipt and does not run again.
- A Rooms session tells the access that sent a request what that request was (`effect-intent`) when the access holds the request's own rights, so a collaborator can give back a receipt it no longer has the request for. Any other access learns no request, and listing pending requests or resuming one still needs the administrator's rights. Any access can list the operations of its own receipts that still hold a place (`held-effects`), which names nothing else.
- Dependencies move to their current releases. The development container takes Rust 1.100, Node 26.13.1, Bun 1.4.5, Playwright 1.65.1, uv 0.13.9, and ruff 0.17.6, so rebuild it. The Rooms server image takes the current Distroless base, the relay's TLS build takes Mbed TLS 4.3.0, and the iroh transport takes iroh 1.5. The CLI's REPL takes libvaxis fixes for key parsing, wrapping, and terminal restore.
- In the Rooms Rust libraries, releasing a session receipt answers a `Release` value, `Released`, `Running`, or `Kept`, where it returned nothing and refused while the session still held the operation's executor. `attached::View::release_line` and `release_open` return it. `Running` changes nothing, and neither does `Kept`, for a result the workspace already adopted. Releasing a stalled request ends it and keeps its receipt, settled as released. A program that releases a receipt reads the answer.

### Fixed

- Rooms trace and rendezvous process tests wait for a closed relay connection to free its slot. A slow close could make release validation fail with HTTP 503.

- A Rooms bot keeps its queued reply when its nickname has reappeared in the room but its restarted session is still taking its seat. The session reports `room-joining` and the bot posts the reply once the seat is ready.

- A Rooms bot now checks which action IDs it issued before settling receipts. A session restoring its room membership keeps its receipt and can finish joining. Use a fresh ID for each new request and issue separate access links to independent clients.

- A Rooms access can open and drop successive readers without exhausting its continuation limit. A Host now releases an actor’s projected export once its partner and the session’s local work have finished with it.
- A process that dies without closing its listener (abort, `SIGKILL`, out of memory) no longer keeps its port bound on Linux. The io_uring backend held an accept on the listening socket, and the kernel kept the socket until it retired the ring, so a restart in place on the same port could fail with "address already in use" after the process was gone. Listeners now wait in an epoll set the ring only watches, and the port is free as soon as the process is. A provider whose listener readiness descriptor is a listening socket, as the TCP and onion providers' are, waits there too. A driver provider package whose resident readiness descriptor is a listening socket is now refused at registration with `ReadinessDescriptorListening`, and the multiplexed transport's `readiness_fd` documents it. If the watch the ring keeps on those listeners ever fails, the loop reports the kernel's cause once, new listener work refuses with it, and closing still completes.
- A restarted `rooms-session` no longer exits with "session lifetime is still pending". Start waits for its lifetime to confirm before its first private write, so a slow or busy storage lane delays the start and no longer refuses it.
- Reloading a Rooms page on a private room while its server restarts keeps you in that room. Before, a reload that found the server down sent you to the join card.
- `glowcap ocapn listen --once` and `--publish` exit with the protocol-abort or timeout code when their one partner's session fails, rather than 0. In MCP and the REPL, `info` reports that session's cause as `listener_stopped` rather than "served its one partner".
- A `rooms session` send, direct message, room join, or directory registration that saves while the session's supervisor is also saving now plans its change again and keeps it. Before, it reported a failure, even after the command had committed, and named a recovery that could never succeed. Saving a session access that keeps losing to other writes now says so and asks for another try, instead of reporting a peer failure.
- `rooms-session start` reports a directory whose saved data it cannot read in the same words as `rooms-session serve`, which end with the next step: start a new session in its place.
- The Rooms bot has a fourth agent verb, `actions`, which lists what the turn's earlier actions did from the bot's own record (`settling`, `posted`, `nothing`, or `unknown`). An agent whose verb its harness ended learns from it what happened, without repeating the action. It sends nothing and takes no place.
- Each Rooms bot verb runs on one budget of at most 100 seconds, or what is left of the turn less 30. A verb that finds 40 seconds or less of the turn left refuses at the start with nothing sent and no place taken.
- A Rooms bot claim in `turn-actions/` names the verb process that wrote it. While the turn runs, the serving bot settles an action whose verb process is gone from the session's list. The harness ended such a verb at its tool timeout, or it crashed. `actions` and a rerun's prompt now show `unknown` when the session never saw it. They showed `settling` until the next start.
- A Rooms bot start no longer marks claims cut and judges each claim by its verb's process. A verb whose process the bot cannot judge keeps its claim, and `status.last_error` says why.
- Claude Code, Codex, and Pi run an agent's tool commands in a session of their own, so ending a turn ends no command the agent started. A Rooms bot verb ends by its own budget, and any other command by nothing the bot does.
- A Rooms bot verb whose budget ended before the session answered prints no `status`. A verb that gave an unknown action's receipt back prints `"outcome": "unknown"`. A committed action the bot holds the receipt of prints `"settling": "bot"`. A `send` whose line posted and could not be kept reports how its files stand, read before the keep failed, where it reported them unknown. `Error::Unkept` of `rooms-services` carries those `files`, so a consumer that matches it by every field adds `..`.
- A Rooms session that answers an acquisition's `release-result` as still running now asks the executor again for as long as the attached view does. It stores only a final answer under the acquisition's id. `recover --acquisition` therefore asks again instead of replaying `release again`. The acquisition's slot and the receipt's place no longer stay held until a restart.
- A Rooms session no longer keeps a seat for a request whose commit was confirmed absent, so such requests cannot fill every place while `held-effects` lists nothing. Releasing a request whose commit has not settled answers `running` to the access that sent it, whether the request runs or is paused, and releases it for any other access.
- A line the Rooms bot or `View::settle_effect` could not keep because of a failure that clears with time (a lost connection, a paused access, or a workspace that kept moving) keeps its receipt, and the bot's sweep keeps the line later. Only a refusal that never clears gives the receipt back.
- Giving back the receipt of a history erasure that is still pending now answers `running` and changes nothing, including between a failed attempt and its retry, and the receipt reads pending until the erasure completes. Before, it answered `released`, the erasure then could not settle, and history retention could never be chosen again. A permanently failing archive keeps that receipt in one of the session's places, and closing the session fails until the erasure completes.
- A Rooms archive share whose issuer or recipient answers with something the session cannot read now ends as an unfinished request that reads unknown, where it stayed paused for a resume that could only fail again. A receipt records a disposition in a form of one width, so adopting or releasing a receipt cannot be refused because the session is at its byte limit.
- A Rooms page attached to a session you run no longer asks you to reload when the connection drops, as when a phone sleeps or changes network. It dials the session again by itself, keeps your drafts, where you were reading, and the access you manage. A connection that stops answering without closing is now noticed while the page is in view.
- A Rooms page reading the session while its connection is away now says it could not read the session, where it said nothing was sent. A change that went through but whose follow-up read failed says so and that what is shown may be out of date, as a notice instead of a failed press. Dismissing a conversation that was still opening while the connection dropped now leaves it over the connection that replaces it, where the page stayed a member of the room.
- A Rooms page whose connection drops while it opens still opens, and shows the session's link once it reconnects. When the session's link cannot be read for another reason, the page still opens, and Settings says why with **Try now** to read it again.
- An access you manage whose own connection drops says so and offers **Try now**, which also confirms a change you sent to it before the drop. Its card shows how that change ended, however it ended, and a change you sent that never got an answer no longer stops you removing the access: removing it says first that it stops checking the change and doesn't undo it.
- Pressing **Hold** again for a management link whose access lost its connection while saving reaches that access again and saves it, or says why it can't.
- A line the session holds no record of after a drop shows as unconfirmed, and its text comes back to the composer so you can send it again if it is missing.
- A Rooms page whose server starts serving a newer build waits to reload until the reload would lose nothing you picked, typed, or started. Before, it reloaded at once.
- A saved Rooms access restored over a session that closed before it answered now says its session could not be reached, and is tried again once the connection returns. Before, the page said it could not restore the saved link.
- `glowcap apps rooms session start` refuses a `--nick` that differs from the workspace's nickname and names the one it has, instead of reporting success and keeping the old one. A nickname belongs to its workspace, so a new one needs a new `--dir`.
- Two people who go to the same new Rooms room at the same moment both enter it. Before, the one who lost the race to open it could be told that the room is no longer listed, because a room its opener had not yet entered was missing from a lookup by name.
- `deployment logs` accepts the services an override adds, not only `directory` and `session`.
- A direct message opened through a Rooms session link with collaborator rights, from the session page or a bot, now receives the other member's replies. Before, the session refused to set up its receiving side without administrator rights. Opening a direct message with a member who already has an open one, from the session page, a bot, or the terminal, reuses that one and gives the extra route back, even after the directory registers again. When the other member opens one again, it lands in the open conversation, which keeps its history, or else arrives as a new one beside the closed one. The session refuses any change that would open a second, and a workspace that already holds two keeps both working.
- Match release image metadata to the Docker or OCI manifest format when publishing the multi-platform image.
- Reuse the authenticated release lookup when validating installers on shared CI hosts.
- Use the browser's login on the Rooms server's own page and explain when Settings cannot read a server reply.
- Stop a Racket call on the driver loop from waiting forever when its answer arrives just as it starts waiting.
- Stop a Racket server on the driver loop from spinning a core while a session sits idle.
- Highlight a Rooms line that mentions you from the one reading the session uses. A mention inside IRC bold or colour from the IRC bridge now counts, and your own line, including one read back from an archive, never highlights.
- Report a refused `poll` from `Connection.runUntil` and `Connection.closeGracefully` as its own cause, such as `SystemResources`, instead of `ConnectionLost`. A Zig switch over `runUntil`'s errors needs arms for `SystemResources`, `InvalidWait`, and `Unexpected`.
- Report an accept the kernel refuses on a TCP or onion listener, such as for a full descriptor table, as `AcceptRefused` with the kernel's cause, as the driver loop's listeners already do. It was reported as `ConnectionLost`, which means the listener shut down. A refused readiness poll on the listener or in the WebRTC transport keeps its own cause too.
- Report a refused readiness poll on an in-process listener as `AcceptRefused`, as TCP and onion listeners do, rather than `ConnectionLost`, which means the listener closed.
- Keep a listener accepting when one queued connection fails before it is taken, such as with a network error Linux reports from `accept`, as `accept(2)` directs. A TCP or onion listener reported `AcceptRefused`, and a driver loop's listener stopped. `AcceptRefusal` no longer holds `NetworkDown`.
- Stop a `listen` started from the MCP server or the REPL when its listener fails, such as when the kernel refuses an accept for a full descriptor table, and name that cause in `info`. It kept reporting a live listener while spinning a core.
- Keep `glowcap listen` serving when one partner fails its handshake or its session, as a `listen` from the MCP server or the REPL already does. It exited with an internal error.
- Classify a closed `driver.Server`'s `ServerClosed` as `closed` rather than `io`, so a caller choosing by `OperationFailure.classify` reads a stopped listener as stopped.
- Report a call, tell, listen, resolve, or retain naming a capability whose home connection was released as `CapabilityClosed` (`GLOWCAP_ERR_CLOSED`), so a caller can treat it as a lost connection. This holds from a behavior's own turn and through a promise fulfilled to that capability. It was reported as `UnknownCapability` (`GLOWCAP_ERR_NOT_FOUND`), the refusal for an id the Host never issued or has fully released, so a partner whose call a Zig behavior refuses this way now reads `CapabilityClosed`.
- Route a promise target by the promise's state when a behavior's turn has no delivering session (a local call) and in `PendingWorkLease.call`, as a turn that arrived over a session already did. An unsettled promise queues a send or tell, and a forward from a turn with no answer queues as a tell. A forward with an answer or a `PendingWorkLease.call` to an unsettled promise returns `NotResolved`. A broken promise returns `PromiseBroken`, a promise fulfilled to a local actor delivers to it, and one fulfilled to data returns `UncallableTarget`. Each was refused as `UnknownCapability`.

### Security

- Release staging now stops if Git cannot determine whether the checkout has local changes. Previously a failed status check could mark a modified build as clean.
- A Rooms web server configured to issue TURN credentials now charges each issuance against its HTTP start budget before contacting the provider. Static ICE configuration remains available when the budget is exhausted.
- The Rooms deployment image keeps startup bearer links out of service logs. Read them with `glowcap apps rooms deployment links`. Upgrade the host CLI as well as the image so the managed session's health check keeps its use link out of Docker health history. If you run a bot session, copy the health check from the updated override example. Earlier log and health records may still contain working credentials.
- The example bot container drops Linux capabilities and blocks privilege gains when it runs an agent. Existing deployments can copy the two settings into their bot override.
- The Python binding's `rendezvous` extra requires websockets 17.4 or later, the first release that limits how many frames one relay message may span.
- In the Rust binding, a fetch or enliven whose partner answers with something other than a capability fails without showing the name or sturdyref it asked for. Either one holds the secret that grants the access, so the failure now says only `fetch did not resolve to a capability` or `enliven did not resolve to a capability`.
